# Feature Specification: DCU 双精度 PFC 加速与批量灰度导出

公共安装与直接Shell编译、运行命令见[README](../../README.md)。Slurm/Debug仅约束本会话代理的
受管集群执行及私有部署；公共用户不以此为安装前提。下文调度设计保留本次实现/验证背景，
科学公式、FP64、固定输入与容差不受此范围澄清影响。

**Feature Branch**: `master`

**Created**: 2026-10-20

**Status**: Implemented；已验证范围见 [validation.md](validation.md)。

**Input**: 单节点 4 DCU 双精度计算相对纯 CPU 至少 5 倍加速；将灰度批量绘图 Java 程序转为
Python；兼容原输入；保持物理方程与算法；数据与图片采用“前缀-步数”安全命名；支持
MPI+DCU 跨节点；仅做最小测试并比较原 CPU 最终结果；日志包含每一步计算时间。

## 验收口径

- 采用两阶段求解器完整耗时，
  包含启动、初始化、FFT 规划、计算、盒优化、通信、传输、日志与数据落盘，排除排队、编译、
  图片导出和原子后处理；与同型号单节点充分使用 CPU 的原程序比较。
- 比较预先冻结的短程算例及唯一
  性能配对的两阶段最终保存结果，不强制运行生产时长，也不追加生产规模验证作业。

## Constitution Constraints *(mandatory)*

- 遵循 `.specify/memory/constitution.md` 的物理不变、双精度、受管代理执行边界与证据要求。
  范围包含Java灰度绘图迁移到Python和安全输出命名，不扩展为其他Java工具重写，
  不改变数据内容格式或物理算法。
- 原 CPU 科学基准为仓库提交 `c86efb51cf03086fb98897ab8abfe2704a62096e` 的 `src/pfc.c`。
  保留自由能泛函、动力学、离散算子、周期边界、FFT 归一化、时间推进、初始化、诊断与
  盒优化的数学运算和调度语义，保持 FP64；不得以减少科学工作量或降精度获取加速。
- 原输入格式、已有状态数据的读取和两阶段衔接必须兼容；除规范的新文件名外，
  保留原子坐标、邻居信息及 LAMMPS 转换链路。
- 本会话代理进行依赖/程序编译、测试、比较、图片及转换验证、性能测量时，必须通过受管集群提交 `sbatch`
  批处理脚本，在分配的计算节点执行；禁止本机或登录节点直接执行。
  该部署的代理作业必须在脚本头部写入 `#SBATCH --partition=Debug`；不得使用其他分区、分区列表或回退。
  日常脚本只保留顺序构建/运行命令，不加入测试、探针、证据生成或外层计时。
- 仅执行本规格定义的最小验证集，禁止全量测试、参数扫描与无依据的重复测试。
  先通过数值等价和兼容性，再报告性能；本规格的验收要求不代表已经实测通过。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以原输入获得可信的四卡加速结果 (Priority: P1)

研究人员继续使用既有两阶段输入，在单节点 4 张 DCU 上生成多晶石墨烯密度场，
在不改变物理计算的前提下缩短等待时间，并能与原 CPU 结果对照。

**Why this priority**: 双精度数值正确性与至少 5 倍加速是本次迁移的核心价值。

**Independent Test**: 在集群对原 CPU 与 4 DCU 各运行同一个已冻结的短程两阶段算例；
比较两阶段末态、诊断量和盒尺寸。数值通过后，运行唯一代表性性能配对。

**Acceptance Scenarios**:

1. **Given** 具有确定种子、相同科学参数和实际初始场的合法原输入，**When** 分别用原 CPU
   与 4 DCU 完成两阶段计算，**Then** 结果有限且通过规定数值容差，不修改任何物理项或推进方法。
2. **Given** 已通过 V1 短程数值验证且已冻结的代表性工作量，**When** 执行一次 CPU/DCU
   性能配对，**Then** 该配对末态也通过对照，`S = T_CPU / T_4DCU >= 5.0`，并提供原 CPU
   版本、资源、环境与实际执行证据（使用调度器时关联作业）。
3. **Given** 原输入中的输出/诊断间隔和盒优化配置，**When** 启用加速和逐步计时，**Then**
   原有诊断、频域重建和盒优化仍按原顺序与频率发生，不增加改变数值轨迹的物理计算。

---

### User Story 2 - 使用多节点 MPI+DCU 计算同一系统 (Priority: P1)

研究人员能够通过MPI将同一个PFC计算分布到多个节点的DCU上，输出完整全局结果；Slurm为可选调度方式。

**Why this priority**: 跨节点是明确要求，单节点多卡不能替代这一能力。

**Independent Test**: 将短程算例部署至至少 2 个节点，每节点至少使用 1 张 DCU，保持总 MPI
进程数、科学分解和初始场与其 CPU 对照一致；复用已有 CPU 基准，不增加规模扫描。

**Acceptance Scenarios**:

1. **Given** 至少两个节点的合法 DCU 分配，**When** 提交 MPI+DCU 作业，**Then** 不同节点
   均实际参与设备计算和跨节点通信，完成两阶段，且末态通过 CPU 对照。
2. **Given** 分布式计算成功完成，**When** 读取输出，**Then** 全局网格顺序、样本数量和
   文件完整性与单节点计算一致，不产生各 rank 覆盖同一全局文件的错误。
3. **Given** 设备资源不足、设备映射不合法或某 rank 失败，**When** 启动作业或推进，**Then**
   作业明确失败并指出原因，不静默退回纯 CPU 或把不完整输出报告为成功。

---

### User Story 3 - 安全命名并继续使用已有输入与重启数据 (Priority: P1)

研究人员获得可排序、便于批处理的文件名，同时仍能使用历史输入和密度场，不必手工重命名旧数据。

**Why this priority**: 输出重命名必须贯通第二阶段读取、绘图和原子转换，避免破坏既有流程。

**Independent Test**: 复用短程算例的两阶段输入，检查旧重启引用、输出名称与下游读取。

**Acceptance Scenarios**:

1. **Given** 前缀 `step1`、步数 `100`，**When** 保存密度场并导出图片，**Then** 文件分别为
   `step1-100.dat` 和 `step1-100.png`，不再插入 `-t-` 或 `:`。
2. **Given** 未改写的第二阶段输入引用 `step1-t-100.dat`，**When** 原文件存在，**Then**
   读取该精确路径；原文件不存在但对应 `step1-100.dat` 存在时，兼容解析并明确记录实际读取路径。
3. **Given** 前缀包含 `:`、空白或其他不安全字符，**When** 生成输出，**Then** 按规定规范化
   前缀；若造成不同输入或阶段的命名冲突，明确失败，不静默覆盖已有结果。

---

### User Story 4 - 用 Python 批量导出相场灰度图 (Priority: P2)

研究人员使用 Python 绘图工具从相场保存帧批量生成灰度 PNG，无需 Java 绘图运行时。

**Why this priority**: 满足演化观察需求，并消除灰度绘图环节对 Java 程序的依赖。

**Independent Test**: 复用算例中的少量现有帧及最小边界数据，在同一集群验证作业中检查尺寸、
灰度、方向、排序和文件名；不额外运行一套模拟或进行视觉全量回归。

**Acceptance Scenarios**:

1. **Given** 网格宽高及指定起点、正间隔和终点，**When** 批量导出，**Then** 按数值步数处理
   实际存在的帧，生成同尺寸、同前缀同 step 的灰度 PNG，并报告成功/缺失数量。
2. **Given** 一帧有效实数密度场，**When** 绘图，**Then** 最小值映射为黑、最大值映射为白，
   中间值逐帧线性映射；图像上下方向保持既有灰度绘图约定，不转置 x/y。
3. **Given** 常量场或指定范围内缺帧，**When** 批量导出，**Then** 常量场输出全黑图；
   缺帧警告后继续，其余合法帧正常生成；全部缺失或显式单文件缺失时明确失败。

---

### User Story 5 - 从日志查看每一步计算耗时 (Priority: P2)

研究人员能够确定每一步实际耗时，识别慢步，并核查加速比是否包含必要的通信和输出成本。

**Why this priority**: 避免当前只有稀疏累计时间而无法判断逐步性能的问题。

**Independent Test**: 直接检查前述算例日志，不新增计算作业。

**Acceptance Scenarios**:

1. **Given** 某阶段执行 T 次实际推进，**When** 作业成功结束，**Then** 有且仅有 T 条逐步计时
   记录，step 为 `1..T`，带阶段/前缀、秒为单位的耗时及累计时间；初态 0 不虚构推进时间。
2. **Given** 原诊断间隔大于 1，**When** 输出逐步计时，**Then** 每个推进步仍被记录，原能量、
   密度与状态保存频率不变；不同 rank 不重复打印同一步。
3. **Given** 多节点设备异步执行，**When** 报告步耗时，**Then** 反映设备完成、FFT、通信与
   等待后的实际墙钟时间，使用参与 rank 的最慢耗时，不能仅计主机发起计算的时间。

### Edge Cases

- 非法网格、步数、批量区间或非正间隔；空目录与没有匹配文件。
- 密度样本数量不等于 `W*H`、截断文件、非实数或 NaN/Inf；报告错误而不生成误导图像。
- 原输入文件路径包含目录或特殊字符时，仍按原路径读取；只规范化输出 basename 的前缀。
- 旧重启文件与新同名映射文件同时存在时，优先精确原路径；禁止猜测其他不相关文件。
- 两阶段前缀相同、规范化后前缀冲突或目标已存在时，不静默覆盖不同计算的结果。
- 步数 `2`、`10`、`100` 按整数排序；图片不因文件系统字典序错序。
- MPI 划分改变可能影响原初始化和重启归一化；不能把这种差异当作舍入误差，或顺带修改原算法。
- CPU 与 DCU 的参数、输入、输出间隔或工作量不一致时，该配对不能用于声明 5 倍加速。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 求解器 MUST 使用 DCU 执行主要数值计算，保持原有双精度表示与运算；
  不得使用降精度、近似物理项或替代物理算法。
- **FR-002**: MUST 支持单节点 4 张 DCU，并按本规格的性能口径达到至少 5 倍加速。
- **FR-003**: MUST 支持 MPI+DCU 跨节点；设备绑定、全局数据布局、通信和结果输出必须正确。
  多节点能力不附加未要求的线性扩展率或多节点 5 倍门槛。
- **FR-004**: MUST 兼容原输入标签、字段顺序、注释、参数含义及合法值；不要求用户为 DCU
  添加或重写物理输入字段。资源配置与物理输入分离。
- **FR-005**: MUST 保持两阶段算法与调度，包括原守恒/非守恒动力学、局部初始化/重启处理、
  每 100 步频域重建、诊断、状态保存与计算盒优化；不得“修正”其现有数学行为。
- **FR-006**: 新密度场 MUST 只按 `<prefix>-<step>.dat` 写出；`step` 为不补零的非负十进制整数。
  数据内容仍是原工作流的无表头实数文本、共 `W*H` 个样本，x 方向优先，不插入尺寸表头。
- **FR-007**: 输出前缀 MUST 仅含 ASCII 字母、数字、`_`、`-`；将原前缀中其他字符逐个替换
  为 `_`，目录部分不参与规范化。必须检测命名冲突，不以生成另一套旧名称副本规避迁移。
- **FR-008**: MUST 优先读取原输入指定的精确重启路径；对不存在的已知
  `<prefix>-t-<step>.dat` 引用，兼容定位对应安全前缀的 `<prefix>-<step>.dat`，并记录映射。
  无匹配文件时必须失败。新旧数据读取均不得改变原重启的数学归一化行为。
- **FR-009**: MUST 将新命名贯通两阶段衔接、批量绘图及原子转换调用；仍能生成原有坐标、
  邻居信息与 LAMMPS 原子初始构型，不重写这些无关 Java 工具。
- **FR-010**: MUST 提供 Python 灰度导出工具，取代灰度绘图 Java 程序；支持单帧与给定
  起点/间隔/终点的批量导出，且可直接读取当前无表头数据并显式接收网格宽高。
- **FR-011**: 图片 MUST 按 `<prefix>-<step>.png` 命名；支持原工作流历史命名帧的读取，
  输出一律规范化，不要求用户先改写历史数据文件。
- **FR-012**: 灰度图 MUST 使用原网格尺寸与方向，按帧做黑到白线性归一化；常量场全黑。
  仅支持本任务的实数密度灰度图，不扩展复数彩色图、动画、交互界面或其他 Java 工具。
- **FR-013**: MUST 区分可跳过的批量缺帧与应失败的非法/损坏数据，报告文件路径及原因；
  全部缺失不得报告成功。
- **FR-014**: MUST 为每个实际推进步生成唯一计时记录，包含阶段/前缀、step、步计算秒数和
  累计秒数，不受原诊断间隔限制；记录顺序可按 step 确定。
- **FR-015**: 逐步计算时间 MUST 覆盖完成的数值推进、FFT 和 MPI 等待，取最慢 rank 的耗时；
  盒优化按原发生位置单独计时并计入总时间。不得为计时增加能量重算或改变物理更新频率。
  数据落盘与日志开销可以单列，但必须计入求解器总耗时。
- **FR-016**: MUST 分别报告初始化、逐步计算/必要优化及求解器总耗时，保留原自由能、平均
  密度和盒尺寸诊断；日志以可解析的固定字段表达单位，便于 CPU/DCU 比较。
- **FR-017**: MUST 执行且仅执行下述最小验证集。本会话代理的编译与验证只在受管集群
  Debug批作业执行，不使用其他分区或回退；公共用户可按README在自己的环境直接执行。
  失败只能针对失败原因补充检查，禁止自动展开全量测试、参数扫描或规模扫描。
- **FR-018**: MUST 将冻结短程算例及唯一性能配对的两阶段最终保存密度场和诊断量与原 CPU
  对照，不强制生产时长或追加生产规模验证。不得仅凭单步一致、成功退出、图片相似或日志中的
  “加速”字样接受结果。
- **FR-019**: MUST 保存基准提交、输入/初始场、种子、MPI 划分、设备与 CPU 资源、软件版本、
  编译选项、计时范围、可选调度作业身份、退出状态和日志路径；未运行的验收项保持未验证。

### Numerical and Performance Acceptance

**数值比较**：所有用于验收的配对必须使用相同输入、固定非零种子、相同实际初始场与科学
MPI 分解。原随机播种和重启重标度依赖 rank 划分，不能只固定种子就认定初态相同。
比较各阶段末态，并检查诊断时刻的平均密度、自由能和 `dx/dy`；非守恒阶段不强求密度守恒。

默认以保存值逐项检查 `abs(DCU-CPU) <= atol + rtol*abs(CPU)`：

| 比较对象 | atol 上限 | rtol 上限 | 精度背景 |
|---|---|---|---|
| 无表头密度文本中的各样本 | `1e-6` | `1e-5` | 原 `%e` 输出只有约 7 位有效数字 |
| 平均密度、平均自由能、`dx/dy` | `1e-8` | `1e-6` | 原诊断保留 9 位小数，兼顾并行舍入 |

上述数值是保存结果的保守工程验收上限，并非由输出位数直接推导。计划必须在运行前结合
舍入误差与盒优化敏感性论证适用性，必要时收紧；不得根据失败结果放宽。
该标准验证保存结果的等价性，不将低精度文本等价冒充 FP64 内部计算精度证明；FP64 仍是
独立的实现约束。任何 NaN/Inf 或超限均失败。最终转换必须成功，且原子数量与原 CPU 输出
的转换一致。

**性能口径**：原 CPU 在与 DCU 节点同型号的单节点上充分使用可用物理 CPU 核心，
不能故意使用单核或削弱基准；4 DCU 版本使用单节点 4 张实际设备及明确的主机 CPU 配额。
计划必须同时落实 CPU 并行利用与上述初态/科学分解一致性，不能靠改变 rank 相关物理行为
解决配置差异。硬件型号、物理核心数、MPI 配置、代表性网格和每阶段步数在计划中冻结。

`T_CPU` 和 `T_4DCU` 均为相同两阶段求解器进程的完整墙钟耗时之和，
包含启动、初始化、FFT 规划、推进、盒优化、通信、传输、原有诊断与数据 I/O，以及新增日志
开销；排除排队、编译、图片导出和原子后处理。CPU 基准使用原求解器，不为加入逐步计时而
改写基准代码。
物理参数、网格、精度、迭代数及输出/诊断频率必须相同；整体 `T_CPU/T_4DCU >= 5.0`
才满足目标，孤立内核的 5 倍不能替代总耗时门槛。

### Minimal Verification Set

| 验证组 | 最小范围 | 复用及边界 |
|---|---|---|
| V1 数值与流程 | 1 个固定小网格、原 CPU 与单节点 4 DCU 各 1 次两阶段运行 | 每阶段最多 200 步，覆盖第 100 步之后的推进与至少一次第二阶段盒优化；比较两阶段末态、诊断、命名与旧重启引用，并验证最终转换 |
| V2 跨节点 | 将 V1 同一算例在至少 2 节点上运行 1 次 | 各节点实际使用 DCU，保持总 rank 数与科学分解，复用 V1 CPU 基准；不做扩展率扫描 |
| V3 性能 | 100×100nm石墨烯（原转换尺度下4240²，名义100.017534nm），原 CPU/单节点 4 DCU 各 1 次配对 | 两阶段末态也须比较；不得以 V1 小规模结果或单核 CPU 作为 5 倍结论 |
| 附带导出与日志检查 | 从已有场文件选至多 3 帧；复用既有作业日志 | 同一验证作业内补充常量场、缺帧/非法区间及损坏数据的最小检查；不新增模拟或全量图片回归 |

性能验收模拟100×100nm石墨烯；保留原转换尺度
0.7/0.7/7.3/2.46，以ceil(1000Å*7.3/(0.7*2.46Å))=4240取不小于100nm的最小整数网格，
名义尺寸100.017534nm。网格由目标物理尺寸确定，不根据测速结果选择更有利算例。

V1/V3 的网格、种子、步数、输出间隔及资源配置必须在实现前写入计划，运行前不得临时挑选
更有利的案例；单次配对若被明确的外部干扰污染，只允许有记录的定向重跑，不默认执行多轮。
V3 在同一次配对中收集末态和耗时，末态对照通过后才宣称加速达标，不额外预跑一遍代表性案例。
“最终结果”指冻结短程算例及唯一性能配对各阶段的最终保存时刻，
不能用中间快照替代；不强制完整生产时长，也不追加生产规模验证作业。最小验证不要求运行
所有历史示例或完整参数空间。

### Key Entities

- **科学运行配置**：既有输入字段、两阶段参数、种子、初始密度场和影响初始化的 MPI 分解。
- **密度场帧**：网格宽高、前缀、整数 step、无表头实数数据及其原始/规范化文件路径。
- **灰度图片**：对应密度帧的规范化 PNG 名称、尺寸、方向及逐帧灰度映射。
- **步耗时记录**：阶段、step、实际计算耗时、累计时间，以及另列的优化与整体耗时。
- **验收配对记录**：原 CPU 与 DCU 配置、误差结果、总耗时、加速比及实际执行证据；采用Slurm时关联作业。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 冻结的代表性两阶段任务以单节点四卡运行，相对充分使用同型号单节点 CPU
  的原程序，按已确认的完整求解耗时口径达到 `T_CPU/T_4DCU >= 5.0`，且该配对数值先通过。
- **SC-002**: V1、V2、V3 在冻结终点的两阶段末态密度和指定诊断量全部满足既定容差；原 CPU 与
  加速结果均无非有限值，最终原子转换成功且原子数量一致。
- **SC-003**: 至少两个节点实际参与同一计算并成功完成；全局输出恰有 `W*H` 个密度样本，
  无遗漏、重复或分片覆盖。
- **SC-004**: 最小验证中 100% 新密度帧与图片满足 `<prefix>-<step>.dat/.png` 命名，
  不包含冒号等不安全字符；旧输入与旧重启路径按兼容规则工作。
- **SC-005**: 选定的至多 3 帧均生成尺寸和方向正确的灰度图，灰度映射最大误差不超过
  1 个 8 位灰阶；常量场、缺失和非法数据按规定处理，灰度导出无需 Java。
- **SC-006**: 对每阶段 T 次推进，逐步日志恰含 `1..T` 的 T 条有限、非负耗时记录，无缺步
  和重复；独立报告求解器总耗时，原能量/密度诊断频率保持不变。
- **SC-007**: 验收仅使用上述最小验证集，保留可追溯的实际执行证据；本会话代理的
  实测限于受管集群Debug批作业，无其他分区回退、本机/登录节点直接测试、全量回归或扫描。
  历史Debug实测结果保留，公共用户的直接运行不受该私有调度规则限制。

## Assumptions

- 本次“至少快 5 倍”按常见加速比定义为 `T_CPU/T_4DCU >= 5`，而非将“快 5 倍”解释为 6 倍。
  目标针对一个预先声明的代表性工作量，不承诺任意小网格均达到 5 倍。
- 原 CPU 基准指当前工作流的 `src/pfc.c`，而非 `source/` 中其他物理模型；Python 迁移只覆盖
  灰度绘图，不覆盖 Coordinator、其他 Java 分析工具和 OVITO/LAMMPS 转换。
- `source/Plotter.java` 的表头/参数接口与批处理调用的 bundled JAR 不一致，不能据源码推定
  JAR 接口。实际求解器输出的无表头数据是本功能必须支持的契约；不要求兼容无关复数格式。
- 兼容原输入指标签、语法、物理含义及历史文件读取兼容；运行前仍需像原工作流一样替换
  `WW/HH/NN/RR/xabc` 等示例占位符，不将占位符当作合法数值输入。
- Python绘图、新命名和最小验证均属于本功能范围。
- [README](../../README.md)提供公开部署说明；实际 DCU 型号、每节点可用设备、CPU 核数、工具链、分布式计算支持、
  执行资源及 Python 图片导出环境需在目标部署确认；历史已验证组合见验证摘要。
- 本规格未选择 DCU API、FFT 实现、Python 绘图库、构建结构或设备通信路径；这些属于计划。
  MPI、DCU、Python、FP64是功能约束；Slurm/Debug只约束本会话代理与私有集群部署。
